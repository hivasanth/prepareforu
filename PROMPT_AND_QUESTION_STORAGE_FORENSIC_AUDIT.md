**PrepareForU — READ-ONLY Audit**

**Evidence convention:** every claim is tagged `[VERIFIED]` (read directly from code/schema/migration), `[INFERRED]` (derived), `[UNVERIFIED]` (could not confirm), `[BLOCKED]` (impossible with available access), with `file:line` references.

## 1. EXECUTIVE SUMMARY

PrepareForU is a React 19 + TypeScript (Vite) SPA backed by a single Supabase project. It has **no in-app AI API client**. All AI "generation" is a **copy-paste bridge**: the app displays/stores prompts, the admin copies a prompt and documents into an external AI tool (NotebookLM / Claude / ChatGPT, opened via `AIToolCards.tsx`), then pastes the AI's JSON output back into the app, where it is parsed, validated, normalized, and written to Postgres.

The audit found:

- **6 in-code prompt constants/helpers** and **33 DB-stored prompt texts** (inside the `prompt_templates` table, which holds **171 live rows**; only 33 of them were rewritten by the canonicalization migration). A **7th legacy DB container** (`question_upload_prompts`) exists but is **not referenced by any application code**.
- **No runtime template interpolation.** Prompts are stored/displayed byte-for-byte; the only string rewrite anywhere is the save-time `promptTopicCanonicalizer` that pins canonical `topic_en`/`topic_te` values inside a prompt's JSON *example*.
- **4 distinct AI→app JSON dialects** enter the Bulk Upload pipeline, all funneled through **one parser** (`BulkQuestionSchema`) → **one visual normalizer** (`normalizeVisualInput`) → **one canonical question model** → **one table** (`questions`). This is a genuine convergence point.
- A **5th JSON dialect** (sub-admin exam wizard, `getPromptText`) does **not** converge: it flows into a separate RPC (`create_teacher_exam*`) and a **separate table** (`teacher_exam_questions`) that stores a **legacy, unvalidated `diagram` JSONB** rendered by a different renderer.
- **Critical visual contract mismatch:** the DB prompts contain a "SUPPORTED VISUAL TYPES" section that teaches a **bilingual `visual` shape (`title_en`/`headers_en`/`rows_en`, `chartType`+`series`)** that the parser **cannot accept** (`QuestionVisualSchema` is English-only + `.strict()`). Any AI output following those examples is rejected. Only the prompts' `visual_engine`/canonical-`visual` structures survive ingestion.
- **Server-side shape safety is inconsistent:** `questions.visual` is strongly validated before insert; `teacher_exam_questions.diagram` has **no shape enforcement** and can be written unvalidated.
- **Ownership is sound for the admin bank** (admin-only insert policy, `created_by` required), and **correctly isolated for sub-admin exams** (`current_sub_admin_id()` RLS). No prompt-generated bypass was found.

**Verdict on the canonical-prompt design question:** `PARTIALLY`. There is clear, single convergence for every *admin bulk upload* prompt and enough understanding of the visual contract to design one canonical Admin Bulk Upload prompt — *but* the report's §26 answers show two structural open risks (the undocumented bilingual-visual dialect and the empty-`visual_engine` trap) and one deliberately separate system (sub-admin exams) that should be excluded from the "one canonical prompt" scope.

## 6. RUNTIME PROMPT SELECTION LOGIC (Admin Bulk Upload)

Exact call chain (all `[VERIFIED]`):

```
AdminBulkParserTopic.tsx (:24 topicId, :43-51 topic resolve, :156 BulkUploadPanel)
  → useBulkUpload (mount effect :498-500 → fetchPrompts :386-392)
      → adminQuestionService.listPrompts (:551-597; cache key `prompts:{exam}:{paper}:{subject}:{topicId??all}` :561; retryWithBackoff)
          → examRepo.fetchPrompts (:491-510)
              → postgrest: prompt_templates WHERE exam_id/paper_id/subject_name[AND topic_id] ORDER BY created_at ASC
```

**Selection decision tree** (`InstructionsTab.tsx:25-26` + `useBulkUpload.ts:380-384`):
1. `promptBlocks.find(b => b.is_default)` → its `prompt_text` — **default flag wins**.
2. else `promptBlocks[0]` (oldest `created_at`) — **first stored prompt wins**.
3. else `subjectName === 'History and Culture' ? HISTORY_PROMPT : GENERIC_PROMPT` — **code fallback**.

**Answers to the audit sub-questions:**
1. Function executing: `fetchPrompts` (hook) → `listPrompts` (service) → `fetchPrompts` (repo). No RPC.
2. Prompt selected: DB row (top 2 rules) else in-code fallback.
3. DB prompt vs code prompt: DB preferred.
4. Fallback: yes — P1/P2.
5. No DB prompt: code fallback chosen by subject name.
6. Selection depends on: subject (History split), exam/paper/subject/topic (DB scoping). NOT on question count, language, or difficulty (none are inputs in this flow — §6 of the prior trace).
7. Multiple prompts combined: **No.** Exactly one prompt is shown/copied.
8. Common prefix/suffix appended: **No.** Byte-for-byte display and copy (`handleCopy` `:484-496`; `InstructionsTab.tsx:75-77`).
9. Modified at runtime: **No.** The only mutation ever applied is at **save time** — `promptTopicCanonicalizer.ts:137-158 canonicalizePromptTopics`, invoked from `PromptEditorModal.tsx:93-96`, rewrites `"topic_en":`/`"topic_te":` **values** inside the prompt's JSON example only (`findSchemaTopicEnPositions` `:38-50`).
10. JSON schema appended at runtime: **No.**
11. Visual instructions appended at runtime: **No.**

## 9. PARSER / VALIDATOR ANALYSIS

### 9.1 `BulkQuestionSchema` (Bulk Upload input) — `src/validations/questionSchema.ts:46-104`
`z.pipe(z.transform(...), z.object(...))`:
- **Transform** (`:46-83`) accepts the 4 dialects:
  - `question_text_en || question_text || question` → `question_text_en` (`:48`)
  - `option_a_en || option_a` … (`:49-52`); if `options` is an array of exactly 4, `[optA..optD] = arg.options` (`:54-56`)
  - `explanation_en || explanation` → `explanation_en` (`:66`)
  - `correct_option || correct` uppercased → `correct_option` (`:68`)
  - `difficulty` lowercased, default `medium` (`:69`)
  - `visual: normalizeVisualInput(arg.visual ?? arg.visual_engine ?? null)` (`:71`)
  - EN fields coerced `.toString().trim()`; empty string on missing (`:62-65`)
  - Telugu/topic fields pass through with `null` fallback (`:75-82`)
- **Object** (`:84-104`): EN content from `questionEnFieldsSchema` (`:9-15`, non-empty strings), `correct_option ∈ {A,B,C,D}`, `difficulty ∈ {easy,medium,hard}`, `visual: QuestionVisualSchema.nullable().optional()`, Telugu optional nullable, `topic_en` non-empty-if-provided.
- **Rejected shapes (would fail):** `answers[]` array; camelCase `optionA`/`questionText` (not aliased); >4 or <4 `options`; bilingual `visual` keys. `[VERIFIED]`

### 9.2 `SingleQuestionSchema` (storage validator) — `questionSchema.ts:17-42`
Used at write-time by `question.repository.ts:206,348` (`validateOrThrow`) on **every** insert/upsert. Adds `exam_id/paper_id/subject_name` required, `negative_marks` range, and canonical `visual`. It validates whatever bulkInsertQuestions passes it — i.e. the same canonical model. `[VERIFIED]`

### 9.3 Invalid-data behavior — six layers
1. `JSON.parse` fail → `{row:0, 'Invalid JSON syntax...'}` (`useBulkUpload.ts:540-545`) — whole batch invalid, no partial.
2. Root not array → invalid (`:547-551`).
3. `BulkQuestionSchema.safeParse` fail → per-row `{row, message}` (`:571-579`); batch marked invalid until rows skipped (`handleSkipRow :637-651`).
4. **Visual throws** inside `safeParse` (normalizer throws) → caught separately as `Row N (visual): ...` (`:565-568`), row dropped-to-invalid, loop continues.
5. Batch-level: `newErrors.length>0` ⇒ invalid even if other rows valid (`:615-617`). Any invalid row = **no preview** until fixed/skipped.
6. At sync: service STRICT REJECT (topic guard `adminQuestionService.ts:440-458`) and DB constraint errors collected per-row (`:499-509`), `success: failures.length===0` (`:521`).

**No partial acceptance; invalid data is rejected row-wise with row numbers; one invalid row blocks the whole batch's preview gate until removed.** `[VERIFIED]`

### 9.4 Topic canonicalization — `src/lib/utils/promptTopicCanonicalizer.ts`
`SCHEMA_INDICATORS` (`:21-28`) detect output-schema regions in a prompt; `canonicalizePromptTopics` (`:137-158`) rewrites **only** `"topic_en"/"topic_te"` example **values** to the canonical `exam_topics` names at save time. Server mirror: `validatePromptTopicContext` (`exam.repository.ts:471-489`) and DB composite FK `fk_prompt_templates_topic_segment` (`live_schema_snapshot.sql:585`) enforce segment integrity. `[VERIFIED]`

### 9.5 Sub-admin safeParse (parallel parser) — `types.ts:185-206`
`JSON.parse` with regex-extraction of `[ {...} ]` and markdown-tick stripping fallbacks — more tolerant than the bulk path; feeds the teacher-exam RPC (not `questions`).

## 19. PROMPT → BACKEND CONVERGENCE ANALYSIS

**Answer: PARTIALLY CONVERGES.**

- **Fully converged path (Admin Bulk Upload):** P1/P2/C1 (and C2 *when AI emits canonical/visual_engine*): different prompts → different AI JSON dialects → **common parser** (`BulkQuestionSchema`) → **common normalizer** (`normalizeVisualInput`) → **canonical question model** → **one table** (`questions`). Convergence is explicit and enforced by `validateOrThrow(SingleQuestionSchema)` at every write (`question.repository.ts:206,348`).
- **Divergent path (Sub-admin exams):** P3 → sub-admin parser → `create_teacher_exam*` RPC → **`teacher_exam_questions`** (separate table, **legacy `diagram`** rather than canonical `visual`). Deliberately separate (teacher-authored exams ≠ admin bank), but it means "one canonical question pipeline" is NOT true product-wide.
- **Dead-end path (C2 visual-mandatory):** prompts that teach the bilingual `visual` shape produce AI JSON that the parser **rejects** — those questions cannot arrive at any table at all.

Convergence for all **bulk-upload** science is real, single-scheme, and safe to build on.

## 29. FINAL AUDIT VERDICT

**"Do we now have enough information to safely design ONE canonical Admin Bulk Upload prompt structure without accidentally breaking another prompt, parser, visual type, or backend storage path?"**

**Answer: YES — for the Admin Bulk Upload scope. PARTIALLY — product-wide.**

**Why YES for bulk upload:**
- All Admin Bulk Upload prompts (P1, P2, C1, C2-when-correct) converge at `BulkQuestionSchema` + `normalizeVisualInput` into exactly one canonical model (`questionSchema.ts:46-104`, `visualNormalizer.ts`), written by one validator (`SingleQuestionSchema`) into one table (`questions`). A single canonical prompt emitting that model cannot break the parser or storage for the bulk path, provided two rules are honored: (a) use the canonical `visual` object (or `visual_engine` mapping), and (b) never emit bilingual `visual` keys or an empty `visual_engine:{}`.
- The parser already accepts every dialect, so a canonical prompt is guaranteed to parse.
- The safe design space is fully mapped: 5 families, 4 accepted dialects, 8 visual types, 1 normalized model, clear STRICT-REJECT topic guard.

**Why PARTIALLY product-wide:**
- The sub-admin exam pipeline (P3 → `teacher_exam_questions` → legacy `diagram`) is a separate storage + render system; a canonical prompt designed for the admin bank must not be assumed to apply there.
- The 138 non-canonicalized live prompt rows are unverifiable from the repo; a rollout should canonicalize all 171 rows (or the live set) before or alongside the new prompt architecture.

**Recommendation ordering:** (1) choose the canonical prompt + canonical visual contract, (2) update the 33+138 DB rows and the 3 in-code prompts to emit it, (3) keep `normalizeVisualInput` as the backward-compatibility bridge, (4) extend the prompt-topics canonicalizer for any new output-schema keys, (5) treat the sub-admin wizard as a separately governed contract.
