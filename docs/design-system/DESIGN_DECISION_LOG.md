>
> **Date convention:** entries use the phase they were decided in (e.g. `Phase 3.2.4`, `Phase 3.3`). Today: 2026-08-02.

| Field | Meaning |
|---|---|
| Decision ID | stable identifier (D-1xx = Phase 3) |
| Date | phase or date |
| Problem | context / problem being solved |
| Alternatives | options considered |
| Final decision | what was chosen |
| Rationale | why |
| Affected components | files/components touched by the decision |

## Phase 3.2.x — Foundation refinement decisions

### D-101 — CollectionCard v1.1 compact premium management row
- **Problem:** Admin Questions needed a dense management list while staying in the premium Card language.
- **Alternatives:** keep the DataGrid; build a new composite; extend Card.
- **Final decision:** `CollectionCard` (Level 2 composite) with `layout="row"` compact two-zone management row; delegates all surface to frozen `Card` (premium mapping). v1.1 added `padding` prop (16/20/24).

### D-102 — CollectionToolbar promoted to premium Card family
- **Problem:** collection page toolbars looked different from premium cards.
- **Alternatives:** neutral translucent bar; own toolbar surface.

- **Problem:** translucent dropdown trigger looked disabled.
- **Alternatives:** keep translucency; make premium filled.

### D-104 — Menu v1.1 (Phase 3.2.4): selected, disabled, elevation-4
- **Problem:** generic dropdown needed selected-row styling and disabled triggers; panel shadow diverged from premium elevation.
- **Alternatives:** style per-consumer; extend Menu.
- **Final decision:** `Menu.Item` gains `selected` (primary text + `bg-primary/20` premium tint); `Menu.Trigger` gains `disabled`; `Menu.Content` shadow `shadow-2xl` → `shadow-elevation-4`.
- **Rationale:** Menu is single owner of dropdown behavior+appearance; consumers style content only.
- **Affected:** `Menu.tsx`, `CollectionFilter.tsx`, NotificationPanel, FilterSelect.
- **Future:** no new dropdown may own its own panel surface.

### D-105 — CollectionFilter v1.1 premium dropdown on Menu foundation
- **Problem:** the finite-set filter was a SelectionContainer+Tabs pill; user requested a premium dropdown matching the User Panel control language.
- **Alternatives:** keep pills; new standalone dropdown.
- **Final decision:** `CollectionFilter` rebuilt on `Menu` (finite-set filter dropdown; compact premium trigger matching search-bar controls; `✓`+primary selected row). Scope: finite sets only; large/searchable lists keep `PremiumSelect`; Exam/Paper/Subject stay on `SelectionContainer`.

- **Affected:** `CollectionFilter.tsx`, `Menu.tsx` (v1.1), `QuestionsActions.tsx` (`label="Difficulty"`).
- **Future:** this scope rule (finite→CollectionFilter, large→PremiumSelect, navigation→SelectionContainer) is permanent.

## Phase 3.3 — Audit decisions (this phase)

### D-106 — User Panel is the sole Golden Reference
- **Problem:** newly created components appeared to diverge from the User Panel.
- **Alternatives:** multiple references (admin, exam, auth); token-only reference.
- **Final decision:** the **User Panel premium `Card` family** is the ONLY visual reference; every surface is classified ✅/⚠/❌ against it. (Audit finding: the "second language" observed in CollectionToolbar/CollectionFilter/Bulk Upload is actually the same premium family with dark-mode token gaps.)
- **Rationale:** single authority prevents reintroduction of competing languages.
- **Affected:** all surface classification in `SURFACE_LAYER_AUDIT.md`.
- **Future:** any new visual language requires a documented exception (like the neutral exam workspace D-108).

### D-107 — One owner per visual layer
- **Problem:** no explicit ownership; duplicates (PremiumSelect panel, toast, tooltip) created second languages.
- **Alternatives:** shared styling layer; per-component freedom.
- **Final decision:** every layer (L0–L17) has exactly one owning Foundation component; components inherit, never create (Surface Creation Audit).
- **Rationale:** prevents overlay/duplication bugs; makes ownership testable.
- **Affected:** ownership matrix + inheritance tree in `SURFACE_LAYER_AUDIT.md`; future components.
- **Future:** new components must pass the Future Component Checklist before implementation.

### D-108 — Neutral exam workspace is an approved exception
- **Problem:** premium mandate vs calm interactive exam workspace.
- **Alternatives:** force premium; keep neutral.
- **Final decision:** interactive exam workspace (`QuestionCard` elevated) stays **neutral**; premium reserved for summary/navigation/dashboard cards. Approved, documented deviation (re-affirmed from Phase 2B).
- **Rationale:** user directive; interaction clarity.
- **Affected:** `QuestionCard.tsx`, exam pages.
- **Future:** exceptions must be registered here before implementation.

### D-109 — Toast is promoted to a Foundation component (L13 owner)
- **Problem:** toast has inline styles, hardcoded fallbacks, no owner, two orphan animation keyframes.
- **Alternatives:** leave unowned; inline-cleanup only.
- **Final decision:** promote a Foundation `Toast` (P1-4) owning L13, token-bound, one animation language; `useToast` API stays backward compatible.
- **Rationale:** every page consumes toast; unowned surfaces are the top source of divergence.
- **Affected:** `useToast.tsx`, toast consumers (all pages).
- **Future:** no inline-styled surface is acceptable going forward.

### D-110 — Dark token gaps are additive token definitions (lowest-governance fix)
- **Problem:** `--elevation-carved`, `--material-card-premium-border`, `--border-gold` are undefined/transparent in dark → premium borders and hover shadows vanish in dark mode.
- **Alternatives:** (a) change frozen component classes (requires freeze re-audit), (b) define missing dark tokens additively.
- **Final decision:** implement P0-5/P0-6/P0-8 by **adding dark token definitions in `themes.css` without touching any component class** — components pick up corrected appearance automatically. Still passes the approval gate.
- **Rationale:** zero component churn; respects the permanent freeze rule.
- **Affected:** `themes.css`, Card premium family, StatCard skeleton family.
- **Future:** any dark-mode-only visual fix prefers additive tokens over class edits.

### D-111 — Radius authority resolves to `@theme` (12/16/20)

### D-121 — Control Family gets per-role semantic tokens (supersedes single `--control-surface`)
- **Problem:** the 3.3A plan proposed one `--control-surface` token for every Control. But Button, IconButton, Input, PremiumSelect, CollectionFilter, Checkbox, Radio and Switch are different semantic roles; forcing all of them onto one shared surface token would recreate the coupling the phase exists to remove (D-120). A single token cannot preserve the distinct certified renders of each role (e.g. Input light surface = `--bg-hover` `#D5B486`; Button Secondary light surface = `--bg-surface` `#C9A070`).
- **Alternatives:** (a) one shared `--control-surface`/`--control-border`; (b) leave controls on generic `--bg-hover-bg`/`--border-subtle`; (c) per-role semantic token namespaces inside the Control family.
- **Final decision:** (c). The Control family is ONE family containing MULTIPLE semantic roles (analogous to Status: success/warning/danger/info share a family but not colors). Each role owns its own token namespace:
  - `--button-*` — Button language (golden: User Panel CTA Button `AntigravityButton.tsx`).
  - `--input-*` — Input language (golden: User Panel search Input + PremiumSelect `AntigravityForm.tsx`/`PremiumSelect.tsx`).
  - `--filter-*` — Filter language (golden: Exam Selection interaction; canonical filter language for the repo; CollectionFilter uses these ONLY, never Card/Button colors).
  - `--checkbox-*` — Checkbox language (golden: certified `SelectionCheckbox`).
  - `--radio-*` — Radio language (golden: certified Radio).
  - Component mapping: Button→`--button-*`; Input/PremiumSelect→`--input-*`; CollectionFilter→`--filter-*`; Checkbox→`--checkbox-*`; Radio→`--radio-*`.
- **Rationale:** each role keeps its proven certified appearance (identical-render gate of D-120 holds per-role); no Control inherits another family's tokens; no new colors are invented (values are re-anchored to existing primitives); future controls evolve independently. Prevents a single token from coupling unrelated controls.
- **Affected:** `themes.css`, `index.css` (@theme), `AntigravityButton.tsx`, `AntigravityForm.tsx`, `PremiumSelect.tsx`, `CollectionFilter.tsx`, `Menu.tsx`, `FOUNDATION_TOKEN_OWNERSHIP.md`, `FOUNDATION_VISUAL_FAMILIES.md`, `FOUNDATION_COMPONENT_FAMILY_MAP.md`, `FOUNDATION_FAMILY_IMPLEMENTATION_PLAN.md`.
- **Future:** the old single-token `--control-surface`/`--control-border` plan is superseded and must NOT be reintroduced; every new Control picks the correct role namespace (or adds one via a new decision entry).

### D-122 — Phase 3.4 P0 does NOT add dark `--elevation-carved` / dark `--border-gold` (G3/G4 deferred)
- **Problem:** the 3.3A plan listed P0-1/P0-2 (3.3A-G3/G4) — add dark values for the light-only `--elevation-carved` and `--border-gold` tokens.
- **Final decision:** **defer both, do not add dark values.** Phase 3.4 P0 (D-121) creates the per-role Control namespaces WITHOUT adding these dark primitives.
- **Rationale:** both tokens are referenced from the dark `:root` scope by FROZEN component material — `--elevation-carved` by `--material-card-premium-shadow` (frozen `Card` premium, DS-001), `--border-gold` by `--material-tab-track-border`/`--material-tab-pill-border` (frozen `Tabs`, DS-011). Today those undefined vars fall back to the certified dark state (`box-shadow: none` / `currentColor`), which is exactly what the certified dark renders ship. Adding dark values would RE-INTRODUCE visible carved shadows / gold border lines into frozen dark renders — a redesign of frozen components, forbidden by the Permanent Freeze Rule and D-120's identical-render gate. The gap is latent, not a bug: the dark fallback IS the certified render.
- **Affected:** `FOUNDATION_VISUAL_FAMILIES.md` §9 (G3/G4 → DEFERRED), `FOUNDATION_FAMILY_IMPLEMENTATION_PLAN.md` (P0-1/P0-2 → deferred), `PHASE_3_4_P0_IMPLEMENTATION_REPORT.md`.
- **Future:** re-evaluate ONLY inside a new frozen-aware decision that explicitly approves a Card/Tabs dark render change.

### D-123 - The application theme is the sole source of truth for Foundation styling (Phase 3.4 P1 B-1)
- **Problem:** no `@custom-variant dark` is registered (`index.css` registers only `@custom-variant light` at line 8), so every `dark:`-prefixed utility resolves to Tailwind v4's default `prefers-color-scheme: dark` **OS media query**, decoupled from the app theme (`ThemeContext` toggles only a `.light` class; `:root` is the dark baseline). `Button` dark variants (primary/success/danger/soft/auth-*) are ENTIRELY `dark:`-gated (`AntigravityButton.tsx:63-83`), so under app-dark + OS-light they render with no surface (no bg, no border, no shadow, `dark:text-white` also fails). `IconButton` theme variant and the `Tabs` pill share the same root cause.
- **Final decision:** approved as an architectural bug fix, not a redesign. The app theme is the only source of truth; the OS must never determine whether Foundation styling appears. For React-branched components (`Button`, `Tabs` pill, `IconButton` theme), strip the `dark:` prefixes and/or branch on `isDark` so the active theme's class string matches its certified render. Do **not** register a `dark` custom variant (no `.dark` class exists; dark = absence of `.light`).
- **Rationale:** render-neutral for the certified configurations (app-dark + OS-dark, app-light + OS-light); repairs the app-dark + OS-light configuration where primary/success/danger/soft buttons were invisible. `dark:`-prefixed classes inside React theme branches were redundant even when they matched.
- **Affected:** `AntigravityButton.tsx` (`darkVariants`, `auth-muted` light string, `IconButton` theme variant), `AntigravityData.tsx` (`Tabs` pill), `FOUNDATION_COMPONENT_AUDIT.md` (H-1).
- **Future:** never use a `dark:`-prefixed utility to gate app-theme styling; use the registered `.light` custom variant or React `isDark` branching.

### D-124 - Permanent family-ownership rules + Amber Color Policy (Phase 3.4 P1)
- **Problem:** the repository needs permanent rules preventing a component from adopting another family's visual identity by sharing a token, and to regulate the warm amber `#C9A070` (the old `--bg-surface` light value).
- **Final decision:** adopt permanently:
  1. **Control** components must NEVER inherit Surface language. Buttons are Buttons; Inputs are Inputs; Filters are Filters; Checkboxes are Checkboxes; Radios are Radios. Their appearance is owned by their own semantic role.
  2. **Surface** components own structure only: Surface, Border, Radius, Elevation, Shadow. Nothing else.
  3. **Navigation** components own the navigation language: SelectionContainer, Tabs, Sidebar, navigation pills, active indicators.
  4. **Status** components own semantic meaning: Badges, Difficulty, Alerts, Toasts, Status Chips.
  5. **Amber Color Policy (permanent):** `#C9A070` or any token derived from the old `--bg-surface` must NOT become the default visual language. Buttons/Filters/Inputs/Selects/Checkboxes/Radios must NEVER inherit this color. Amber may remain only if it satisfies ALL of: (a) belongs to a documented Foundation family, (b) has a clear semantic purpose, (c) is the Golden Reference for that family, (d) is explicitly approved in this log. Otherwise it is scheduled for migration.
- **P1 amber compliance audit:** light-mode Control role tokens currently reference amber — `--button-surface-secondary` (`#C9A070`), `--button-border-secondary` (`--border-gold`), `--checkbox-surface` (`#C9A070`), `--checkbox-border` (`--border-gold`) at `themes.css:1210-1217`, and `--filter-surface` (= `var(--bg-surface)`). These are the certified golden "Family B" light material; they satisfy (a)-(c) but the new "Controls must never inherit" rule is in tension → **scheduled for migration** (a future render change requiring new design approval). No action in P1 (render-neutral gate). Long-term objective: Surface → premium structural surfaces; Control → control language; Navigation → exam-selection language; Status → semantic colors.
- **Affected:** `FOUNDATION_TOKEN_OWNERSHIP.md`, `FOUNDATION_VISUAL_FAMILIES.md`, `FOUNDATION_COMPONENT_FAMILY_MAP.md`, `FOUNDATION_COMPONENT_AUDIT.md`.
- **Future:** every new component must follow its family's language; amber migration candidates are tracked in the P1 report.
